Scope: repository setup, install reproducibility, static checks, production build,
public-route smoke testing, responsive navigation, authentication flows, Supabase/RLS
review, and Stripe tip reconciliation.

- `tsc --noEmit` passes.

## Confirmed findings and proposed fixes

### P0 — Stripe retries can be acknowledged before reconciliation succeeds

The webhook inserts `payment_events` before updating the related tip. If the tip update
or the final ledger update fails, Stripe retries encounter the unique event ID and return
`200 ok` without retrying reconciliation. A transient database failure can therefore
leave a real payment permanently stranded.

Proposed fix:

1. Treat an existing event as complete only when `processed_at` is populated.
2. Retry unprocessed events and check every database result.
3. Mark the ledger processed only after the tip transition succeeds.
4. Add unit coverage for completed, duplicate, retryable, and invalid events.

### P1 — Stripe signature and payment assertions are incomplete

The custom verifier accepts signatures without Stripe's five-minute timestamp tolerance
and only considers one `v1` signature. The handler also marks a tip paid from the event
type and metadata alone, without requiring `payment_status = paid` or matching the
Checkout Session ID, amount, and currency to the stored tip.

Proposed fix:

1. Enforce a five-minute timestamp tolerance and accept any valid `v1` signature.
2. Validate the event envelope before privileged database access.
3. Require the stored tip to match the Checkout Session ID, amount, and currency before
   transitioning to `paid`.
4. Propagate the tip ID to PaymentIntent metadata for refund reconciliation.

References: [Stripe webhook guidance](https://docs.stripe.com/webhooks) and
[Checkout Session fields](https://docs.stripe.com/api/checkout/sessions/object).

### P1 — Password recovery has no password-update state

Reset emails return users to `/login`. Once Supabase restores the recovery session, the
login page immediately redirects to the dashboard and never calls
`auth.updateUser({ password })`. Users can request a reset link but cannot choose a new
password.

Proposed fix:

1. Return recovery links to an explicit login recovery mode.
2. Render and validate a new-password form in that mode.
3. Update the password, sign out the recovery session, and send the user back to normal
   login after success.

### P1 — Clean npm installs are broken

`npm ci` exits with `EUSAGE` because `package-lock.json` is not synchronized with
`package.json` (missing locked dependencies include `ajv`, `lru-cache`, and
`json-schema-traverse`). Bun is not installed in the current environment, so the
committed npm workflow is not reproducible.

Proposed fix: regenerate `package-lock.json` from the declared dependencies and verify a
fresh `npm ci`.

### P1 — The lint gate is not currently enforceable

ESLint reports 10,348 Prettier errors across 90 files on Windows, largely because the
repository has no cross-platform line-ending policy. With line endings ignored, Prettier
still finds substantive drift in 37 files. There are also 10 non-blocking React Refresh
warnings.

Proposed fix:

1. Add a checked-in Prettier configuration with cross-platform end-of-line handling.
2. Format the repository in a separate mechanical commit.
3. Add `typecheck`, `test`, and aggregate `check` scripts so local and CI commands match.

### P2 — Build uses a deprecated TanStack Start API

The production build warns that `createServerFn().inputValidator()` is deprecated.

Proposed fix: replace it with `createServerFn().validator()` and cover the validator in
the payment tests.

### P2 — Public product messaging is stale

The home page and footer describe the app as a “Phase 0 foundation” with “No backend
connected yet,” while the repository contains active Supabase integration, migrations,
authentication, marketplace, live, admin, and payment code.

Proposed fix: replace implementation-status copy with stable product-facing language and
remove the obsolete phase labels from public pages.

### P2 — No automated repository QA workflow

The repository has no test script or GitHub Actions workflow even though Phase 1–4 code
is present.

Proposed fix: add focused unit tests for the payment boundary and a CI workflow that runs
clean install, typecheck, lint, tests, and production build.
